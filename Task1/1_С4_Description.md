# BionicPRO — задача 1

## Цель
Доработать контейнерную диаграмму C4 так, чтобы она обеспечивала:

- унифицированный доступ во все пользовательские каналы BionicPRO;
- возможность использовать внешние источники учётных записей в стране представительства;
- соблюдение принципа локального хранения персональных и медицинских данных;
- безопасную работу с access token и refresh token без передачи токенов IdP на фронтенд;
- возможность подключать разные внешние удостоверяющие службы в разных странах.

---

## Предлагаемое решение

В целевой архитектуре вводится отдельный сервис **bionicpro-auth**, который становится единственной точкой взаимодействия клиентских приложений с контуром аутентификации.

### Основная идея

Вместо прямой схемы:

`Frontend -> Keycloak`

используется схема:

`Frontend -> bionicpro-auth -> Keycloak -> External IdP / LDAP`

Это означает, что:

- фронтенд больше не получает `access_token` и `refresh_token`, выданные Keycloak или внешним IdP;
- обмен `authorization code` на токены выполняется только на серверной стороне;
- клиент получает только защищённую сессионную cookie;
- Keycloak выступает как **центральный брокер идентификации**, а не как единое хранилище всех чувствительных пользовательских данных.

---

## Компоненты

### 1. bionicpro-auth
Новый backend-сервис аутентификации и управления сессиями.

Функции сервиса:
- инициирует вход пользователя;
- перенаправляет пользователя в Keycloak;
- принимает `authorization code` на callback;
- обменивает `code` на `access_token` и `refresh_token`;
- сохраняет токены в server-side session storage;
- возвращает фронтенду только защищённую cookie;
- в дальнейшем сам обновляет `access_token` через `refresh_token`.

### 2. Keycloak IAM
Keycloak используется как центральный IAM/Broker BionicPRO.

Функции Keycloak:
- единая точка входа для систем BionicPRO;
- поддержка identity brokering через OIDC/SAML;
- поддержка LDAP federation;
- выпуск токенов для внутренних сервисов;
- централизованная работа с ролями, MFA, client policies.

### 3. Session Store
Используется Redis или другой распределённый кэш.

В нём хранятся:
- `session_id`;
- действующий `access_token`;
- `refresh_token` в зашифрованном виде;
- срок действия токенов;
- привязка токенов к пользовательской сессии.

### 4. External Country IdP
Внешний удостоверяющий сервис представительства BionicPRO в другой стране.

Он остаётся источником истины для учётных записей локальных пользователей. Keycloak интегрируется с ним через identity brokering.

### 5. Country LDAP Directory
Локальный LDAP-каталог представительства.

Используется для:
- проверки учётных данных;
- получения групп и ролей;
- унификации ролей между представительствами через маппинг в Keycloak.

### 6. Regional Patient Data Store
Локальное хранилище персональных и медицинских данных.

Такие данные **не должны переноситься в центральную IAM-систему**. Это нужно для соблюдения требований локального законодательства по медданным и персональной информации.

## Логика работы

### Сценарий аутентификации
1. Пользователь открывает Android/web-приложение BionicPRO.
2. Клиентское приложение обращается в `bionicpro-auth`.
3. `bionicpro-auth` инициирует вход через Keycloak.
4. Keycloak:
    - либо аутентифицирует пользователя локально,
    - либо перенаправляет пользователя во внешний национальный IdP,
    - либо использует LDAP federation.
5. После успешного входа Keycloak возвращает `authorization code` в `bionicpro-auth`.
6. `bionicpro-auth` обменивает code на `access_token` и `refresh_token`.
7. Токены сохраняются в `Session Store`.
8. Во фронтенд отправляется только сессионная cookie с флагами `HttpOnly` и `Secure`.

### Дальнейший доступ к защищённым ресурсам
- фронтенд прикладывает только session cookie;
- `bionicpro-auth` извлекает токены из server-side session storage;
- если `access_token` истёк, сервис сам выполняет refresh через `refresh_token`;
- фронтенд не участвует в токен-обмене и не хранит токены у себя.

## Почему такое решение соответствует требованиям

### 1. Унификация доступа
Для всех приложений BionicPRO вход становится единым: клиент работает с `bionicpro-auth`, а тот — с Keycloak. При этом реальные учётные записи могут находиться во внешних системах разных стран.

### 2. Соблюдение принципа локального хранения данных
В контур аутентификации не переносятся медицинские записи, телеметрия и полные профили пациентов.

Центрально хранятся только:
- идентификатор пользователя;
- внешний идентификатор учётной записи;
- страна / представительство;
- роли и группы;
- технические параметры аутентификации.

Персональные и медицинские данные остаются в региональных системах.

### 3. Безопасная работа с токенами
Токены IdP не попадают на фронтенд. Это снижает риск их компрометации через XSS, утечку из localStorage/sessionStorage или через небезопасный клиентский код.

### 4. Поддержка разных удостоверяющих служб
Keycloak позволяет подключать разные механизмы аутентификации:
- OIDC IdP;
- SAML IdP;
- LDAP/AD;
- локальные учётные записи.

Таким образом BionicPRO может подключать разные представительства без изменения клиентских приложений.

## Изменения на диаграмме C4

В обновлённую контейнерную диаграмму добавлены:

- `bionicpro-auth`;
- `Keycloak IAM`;
- `Session Store`;
- `External Country IdP`;
- `Country LDAP Directory`;
- `Regional Patient Data Store`.

## Вывод

Предложенная архитектура позволяет одновременно решить две задачи:

1. централизовать и унифицировать аутентификацию в BionicPRO;
2. не нарушить требования по локальному хранению чувствительных данных в разных странах.

Ключевым архитектурным изменением является ввод сервиса `bionicpro-auth`, который выносит работу с токенами на серверную сторону и исключает передачу токенов внешних IdP на фронтенд. Keycloak при этом используется как единый IAM-брокер с поддержкой внешних удостоверяющих служб и LDAP federation.
